# The Harness Glue Is Provably Confined: No Network, Writes Only to Declared Roots

**Status:** Accepted

## Context

The harness glue is stdlib-only Python plus thin Bash, across two trust tiers. The **shipped runtime** (`core/scripts`, `stacks/`, hooks) executes on a consumer's machine. The **producer tooling** (the loose `harness/*.py`, the battery, and the `tools/` user-level tools) runs on the maintainer's.

A future edit could silently add a socket, spawn `curl`, or write outside the trees a tool is meant to rewrite. Two existing gates leave the gap. The stdlib-only scan (1c) proves no third-party import; the import-boundary gate (1g) proves a one-way module graph. Neither proves the glue reaches no network, nor confines where it writes.

**Scope boundary.** This validates the harness's *own* glue code, not agent behavior. Confining what an agent does at runtime is `tools/claude-dev`'s container egress boundary ([default-deny-pod-host-egress](2026-07-17-default-deny-pod-host-egress.md)) — a separate boundary. Do not conflate them.

## Options Considered

1. **Trust review** (status quo) — rejected: a socket import or a stray `write_text` is exactly the regression review misses; the invariant wants an engine.
2. **A runtime audit hook** (`sys.addaudithook` / PEP 578) installed during the battery's suite run, enforcing both invariants dynamically — rejected. (a) Battery step 4 spawns the suites as child processes, so a hook in the battery process observes none of the code under test. PEP 578 hooks are also non-removable, so one installed in-process leaks into later steps that legitimately write outside `.scratch/` (materialize rewrites `samples/`, package-marketplace rewrites `plugins/`). (b) The shipped suites themselves use `tempfile`, `write_text`, and spawn `sys.executable`, so the hook fails the currently-green battery on day one; exempting tmpdirs, `__pycache__`, and `sys.executable` makes it near-vacuous. (c) Audit-event mechanics (`os.open` flag bits vs `io.open` mode string, `os.rename`/`replace`, `os.system`) are error-prone. A correct version needs a child-runner injecting the hook per spawned interpreter — materially larger.
3. **Configuring the battery's existing linters** (ruff's `banned-api` with per-file ignores; bandit's subprocess/urllib findings) — rejected as a replacement. They cover only the import half: a banned-module list with per-file exemptions. Neither can express the per-file argv0 allowlists, the (subcommand, URL-prefix) egress pairs, the write-capability set routed through `write_guard`, the bash git scan, or the staleness rule. The exemptions would also scatter into tool config — against the one-manifest-with-a-why decision below. Bandit's relevant findings sit below the battery's `-ll` severity bar, and `# nosec` is deliberately disarmed (1b), so it offers no sanction mechanism either. The linters stay what they are: generic pattern checks beside a project-specific policy gate.
4. **A static gate plus a producer write choke-point** (chosen) — proves the realistic surface at the commit gate, where a regression is cheapest to fix, at zero cost to consumers.

## Decision

**Two static battery gates plus a runtime write choke-point confine the glue: no network egress, and writes only to declared roots.**

**No-network gate (step 1h, `check_no_network`).** Over both tiers: no network-module import (`socket`, `urllib`, `http`, `ssl`, `webbrowser`, …); no `os.system`/`exec`/`spawn`; no `pty`; no literal dynamic import of a network or spawn module. Bash is scanned for named network CLIs (`curl`, `wget`, `gh`, `ssh`, …) and for git network subcommands, with backslash continuations folded first. Quoted text is data (release-version's printed push hint); a `$(…)` or backtick substitution executes even inside quotes, so it is scanned. Spawning is itself a sanctioned capability: `subprocess` may be imported only in a `[[sanctioned_spawner]]` manifest file — six today, each pinned to an argv0 allowlist (`git`, `sys.executable`). The import rule is alias-proof by construction: an import statement names the real module however it is aliased. That closes the spawn surface as a class. Inside a spawner, argv must be a list literal — positional or the `args=` keyword — with argv0 on the file's allowlist. Shell-string commands, including the `subprocess.getoutput` pair, are rejected outright. An unlisted CLI fails without needing a denylist entry. `sys.executable` may run `-m` only for `unittest` (materialize's suite discovery); `pip` above all is refused. A literal git-network subcommand fails on the shipped tier — anywhere in argv, so an option like `-C` cannot hide it. The producer tier allows exactly one egress: git `ls-remote https://github.com/…` (deps-report's version check) — git reaching a git remote, not a raw socket. The loader refuses an egress prefix that is not an https://, origin-bounded URL, so a sloppy entry cannot widen the sanction.

The producer tier also covers every user-level tool under `tools/`, enumerated from the directory so a new tool cannot land unscanned. `harness-stats` is clean; `claude-dev` (then `claude-pod`) is network-facing by design — its `ide_preflight.py` probes the IDE's loopback MCP port. That file is a `[[sanctioned_network]]` manifest entry: exempt from the import check only, still barred from spawning a network CLI. A stray Python network import or named-CLI spawn elsewhere in `tools/` is caught. The bash CLI scan is a named denylist, not an allowlist: package and container managers (`docker`, `pip`, `npm`) sit outside it — its bash is docker-driven by design, and bash carries no per-file sanction kind (see the ceiling).

**Confined-writes gate (step 1i, `check_confined_writes`) plus `harness/write_guard.py`.** `write_guard` exposes `write_scope(*roots)` — a `ContextVar`-based context manager — and guarded verbs (`mkdir`, `copy`, `write_text`, `remove_tree`, `unlink`). Each entry point declares the roots it may write under; `_guard` rejects any resolved path outside them, and fails closed when no scope is open. `write_text` is atomic (temp + `replace`) and keeps an existing target's mode — a filled executable skeleton keeps its `+x`. The delete verbs act on the entry itself, never through a symlink. The static gate bans raw write primitives outside the manifest's sanctioned-writer allowlist, forcing the four tree-rewriters (`materialize.py`, `init.py`, `package-marketplace.py`, `render-agent-mirrors.py`) through `write_guard`.

The pairing is the point: static proves the choke-point cannot be bypassed (it cannot see computed paths); the runtime guard confines the resolved destination (it sees only executed paths). Neither achieves alone what the two achieve together.

**Sanctioned writers** (raw writes allowed): `write_guard.py` itself, plus the three refreshers — `refresh-gitignore.py` and `claude-md/refresh-chapters.py` (consumer-shipped), `refresh-settings.py` (consumer-executed). Each is stdlib-only with a single argv target, so it cannot import `write_guard`. The three shipped-runtime writers (`handoff.py`, `grading/handoff_facts.py`, `changeset/git_facts.py`) write under `.scratch/` — `handoff.py`'s `--file` is caller-directed, defaulting there.

**One explicit policy file.** The sanctioned exceptions — writers, spawners, egress, and network files — span parts (`harness/` core, producer, `tools/`), so they are not code constants scattered through the gate. They live in one manifest, `harness/confinement-policy.toml`, loaded into a frozen `ConfinementPolicy` record (read-only mappings, immutable all the way down) at the parse boundary. The mechanism is a module pair: `checks/confinement.py` (the gate — manifest record, scan targets, bash scan, the two steps) over `checks/confinement_ast.py` (the policy-free detectors, taking sanctions as parameters). The policy — what is deliberately allowed, and why — sits in one place a maintainer or auditor reads at a glance. A manifest entry naming a missing file fails the gate. So does one naming a file outside the scan targets (test scaffolding, the checker): a sanction never enforced is dead, not latent. So does a stale one: a writer with no write capability left, a spawner with no `subprocess` import, a network file with no network-module import, an egress pair no call exercises. The manifest is the exact sanctioned surface, never an accumulating one.

**Capability resolution, not name-matching.** Both gates resolve each file's import bindings (`_import_bindings`). For writes, one capability fires however it is spelled: a module alias, a from-import, `io.open`/`codecs.open`, the `Path` write methods (`rename`/`replace`/`touch`/`rmdir`/`chmod`, the link pair). So do the raw-fd/`tempfile` forms, the metadata writes (`os.chmod`/`chown`/`utime`), the logging file handlers, and the compression writers. A write-mode literal fires; a tar `"r:xz"` read does not. A present but non-literal mode fails closed — `open(p, MODE)` cannot de-gate a write. Where the import itself is the capability — `sqlite3`, `dbm`, `shelve` create their backing file with no labelable call — the import is banned outside sanctioned writers. For spawns: `import subprocess as sp`, `from subprocess import run`, `from os import system`, and a literal `import_module("subprocess")` fire like the spelled-out forms. The sanction check fires at the import site; the argv rules at the call site. An ordinary refactor cannot slip a write or a spawn past the gate. The `write_guard` skip trusts the resolved module, not a receiver name, so a shadowing local still trips the gate.

**Static ceiling** (noted honestly). The two shipped git gateways call `["git", *args]` with a dynamic subcommand, so static pins only `argv0 == "git"` there. The subcommand is trusted via the import-boundary gate (1g) that funnels all git through the gateway. Genuine reflection stays beyond reach: `getattr` chains, a non-literal `import_module`, a callable rebound to a new name, `sys.executable` running computed code. A writer reached only as an attribute chain (`logging.handlers.X`, `ctypes`, `multiprocessing` running computed callables) is out of reach too. In Bash the ceiling is wider. The CLI scan is a named denylist; an unlisted binary (`docker`, `pip`, a project script) can reach the network unflagged. A quoted command word reaching execution (`eval`, `bash -c`, `"curl" url`) is invisible. The write half (1i) covers Python only — bash writes (`release-version.sh` stamping `VERSION`, the `tools/` installers) stay review-owned. The runtime guard resolves then writes, so a concurrent path swap (TOCTOU) sits outside its threat model: it is local maintainer tooling, not a sandbox. Accepted: the gates cover the lexically visible surface — the regression class review misses. What slips past requires deliberate construction, which is review's job to catch.

## Consequences

- Positive: a network call or a stray write becomes a battery failure at the commit gate, not a review miss. Both checks are static, so they run in `--quick`; the shipped runtime is untouched.
- Positive: `write_guard`'s atomic `write_text` means an interrupted rewrite never truncates an existing file, and a rewritten file keeps its mode.
- Negative: a new writing file fails 1i until it routes through `write_guard` or earns a `[[sanctioned_writer]]` manifest entry. A new spawning file fails 1h until it earns a `[[sanctioned_spawner]]` entry and presents a list-literal argv from its allowlist.
- Non-consequence: zero shipped-runtime code change. The three shipped writers are allowlisted, not choke-pointed — `handoff.py`'s `--file` is intentionally caller-directed, so hard `.scratch/` confinement would be wrong. `write_guard` is pure producer, never copied into a plugin. The gate is `mypy --strict` clean on the producer side.

## Recording a new expected exception

The gate fails closed, so the next legitimate writer or egress trips it by design. Recording that the new behavior is *expected* is a deliberate, reviewed act, not a suppression:

Every exception is one entry in `harness/confinement-policy.toml`, with a `why`:

- A new **writer** routes through `write_guard`, or — if it cannot (stdlib-only, consumer-shipped, single argv target) — earns a `[[sanctioned_writer]]` entry.
- A new **spawner** earns a `[[sanctioned_spawner]]` entry naming the argv0 tokens it may spawn; its argv must be a list literal.
- A new **egress** earns a `[[sanctioned_egress]]` entry — subcommand plus an https://, origin-bounded URL prefix (the loader refuses less).
- A file whose **network access is its function** (like the dev container's MCP probe) earns a `[[sanctioned_network]]` entry. The manifest carries each justification beside the exception, in the one place the gate reads.
- A legitimate **bash** network use has no manifest kind: it edits the named-CLI sets in `checks/confinement_ast.py` by reviewed diff and amends this ADR.
- A change that **moves the trust surface** — a new network destination, a new tier, a shipped-runtime writer — amends this ADR.

Every entry is a battery-gated, reviewed diff: the record and the enforcement move together, and an unexplained exception cannot land silently. The reverse holds too: when the behavior goes, the entry goes with it — the gate fails a sanction no code exercises, so the manifest cannot silently outgrow the surface it records.
