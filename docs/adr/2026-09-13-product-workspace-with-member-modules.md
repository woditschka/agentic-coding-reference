# A Product Workspace Holds the Product Truth; Module Repositories Are Members Checked Out on Demand

**Status:** Accepted (member placement decided 2026-09-18; spike half run 2026-09-18; change 1 of 3 landed 2026-09-19; see Implementation)

> 2026-09-18, spike against the bookstore sample, Claude Code 2.1.x and claude-dev on macOS. A member's rules file is not loaded at session start from a directory added with `--add-dir`; the docs confirm it loads at start only under `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`, and never from a settings-based grant. It is loaded once any file under the member is read: a session in the umbrella that read one backend file then answered from the backend's rules file. The one-line deferral therefore holds and must read correctly inside an umbrella session. Reads of a sibling need no grant at all; the grants gate writes. `--add-dir ../bookstore-backend` accepts the relative path, and a write inside the member succeeded under it where the ungranted control was denied. Whether `permissions.additionalDirectories` accepts a relative path is still open: non-interactive mode ignores settings-based grants until the workspace is trusted, so the check needs an interactive session. `claude-dev access --rw <member>` lists the member as a read-write mount beside the umbrella, and the shipped egress policy already covers the Gradle and Maven hosts a member build needs; a full container launch was not run. `CLAUDE_PROJECT_DIR` stays the launch directory, so the hooks keep the umbrella. OpenCode and Copilot CLI are not installed on the spike machine; their two checks are still open.

## Context

Some products split their modules, a frontend and a backend for instance, across repositories. The harness binds one consumer to one directory: one repository, one docs roster, one gate, one working tree. Three questions arrive tangled when such a product adopts it: where the product truth lives (PRD, system design, ADRs, ubiquitous language), how the product deploys (one unit, or services scaling apart), and who works on what (one team on everything, or teams per module behind an agreed API). A layout that fits one team shape should not be rebuilt for the next.

Two facts shape the decision. The change set under review has one definition, `git diff` in one repository through one gateway (`scripts/changeset/git_facts.py`); the reviewers, the review plan, the security-surface probe, and the change-grader all read it. And Conway's law holds for agents as for teams: what an agent can read, it couples to.

## Options Considered

1. **Git submodules under an umbrella repository.** Rejected: the superproject diff renders an edit inside a submodule as one pointer line, so the reviewers, the risk ladder, and the tree snapshots go blind while the pipeline runs green. Each module also sits on a detached HEAD.
2. **Git subtree.** Every git call works unchanged; syncing to the upstream repositories is a human step at commit time. Kept as the zero-change prototype path; rejected as the design because history noise and the sync burden grow with every member.
3. **Nested checkouts inside the umbrella.** Rejected for three reasons. A member directory carrying its own `.git` enters the umbrella's snapshot and every `git add -A` as an embedded-repository gitlink, so the umbrella's tree sha moves with the member's HEAD. Ignoring the member paths instead hides them from ripgrep-based search, which is what the file tools run. A member's own rules file loads whenever a file under it is read. Kept as the fallback for a tool that cannot add a second root.
4. **Sibling checkouts and a workspace-aware change set** (chosen). Members sit beside the umbrella, never inside it, so the umbrella's tree never carries a member and no ignore rule is needed; the session reaches them through each tool's own directory grant.
5. **Model the deployment topology in the layout.** Rejected: the gate builds and tests, it never deploys, and repositories per module neither force nor forbid separate deployables.

## Decision

**A product workspace is an umbrella repository that owns the product truth and declares its member modules; members are repositories checked out beside it, as siblings, only when a slice needs them.**

- **Product tier.** The umbrella's `docs/` holds the PRD, the product system design, and cross-module ADRs. The product design owns the module map, each module's responsibility, the contracts between modules (APIs, events, data ownership), the cross-cutting concerns, and the shared terms. Deployment topology is a statement in that design and an ADR, never a layout fact.
- **Module tier.** A member repository is a harness consumer in a new *module* role. Its `docs/` holds the module system design (internal structure, aggregates, data model, local terms) and module ADRs; it carries no PRD. References run one way: the product design links each module design; a module design refers up to the contracts it implements and never defines one. The routing rule is mechanical: whatever another team would need to know goes up.
- **Workspace.** A `[workspace]` table in `scripts/layout.toml` lists the members. The git gateway runs each command per present member and prefixes each path with the member's relative path, so every consumer opens a file by the path it is given. A snapshot becomes a member-to-tree-sha map. The gate dispatcher iterates the present members before calling the stack verbs. The doctor reports an absent member without failing. The table also declares each provider's contract paths and each member's dependencies. Design triage refuses a slice that changes a contract while a dependent is absent, and warns when a dependent's contract tests did not run. A single repository is the degenerate case with no members.
- **Placement and access.** A member is a sibling directory of the umbrella: a clone by default, or a worktree when the team wants the shared object store. A worktree's absolute link into its main repository must be reachable wherever the session runs, the claude-dev container included. Each `[workspace]` entry declares the member's path relative to the umbrella. The session reaches a member through the tools' own grants, never through nesting. Two are project-owned and committed: Claude Code's additional-directory permission with the native sandbox's write allow-list in `.claude/settings.json`, and OpenCode's `external_directory` allow rule in its project config. Two are operator-side: Copilot CLI's per-location `allowed_directories` in its user config, which no launch flag replaces, and claude-dev's read-write mount. `init` writes the project-owned grants from the table. The doctor reports a member whose committed grants drifted from the table and a Copilot grant it cannot find; the mount stays the operator's launch policy.
- **Checkout policy.** The umbrella always; members on demand. Not having the neighbor on disk is the mechanism that keeps the contract sufficient. A contract change checks out both sides, which is the whole-product shape for that one slice. Cross-module integration is consumer-driven contract tests defined with the contract, never a shared checkout.
- **One layout.** Prefixed globs classify every member; the security-surface probe is the union of the member languages. A member repository carries no runtime surface of its own: no `CLAUDE.md` beyond one line deferring to the umbrella, and no `.claude/`, `.github/agents`, `.github/skills`, or `.opencode/agents`. Claude Code reads a rules file from an added directory and Copilot CLI loads an added directory's agents and skills as trusted configuration. A team runs one harness level, never both, and every harness session starts in the umbrella.

## Consequences

**Positive:** one mechanism covers the one-team, per-module-team, and agreed-API shapes; they differ only in which checkouts sit beside the umbrella on a machine. Each tier has one decision log and a mechanical routing rule between them. Two teams editing the product design conflict at merge in the umbrella, which is the design conversation the split intends.

**Negative:** the umbrella detects as the generic stack. Each member declares its stack in the `[workspace]` entry, so the engine can compose that member's probe and conventions from the stack's shipped defaults. Until that composition lands, the umbrella's own layout carries the probe. Two consumer roles mean two doctor rosters. The two-tier prose is one managed `CLAUDE.md` chapter rendered for the product role only. Two shipped clauses are the exception: the review planner carries `basis.members` forward and the review workflow names the per-member tree override. A single repository's prompts grow by those two clauses and nothing else. The schema change and the engine fan-out still warrant a tier-2 audit. The member-to-sha snapshot adds an optional `members` object to the review-plan record; a single repository's record is unchanged. A slice lands as one commit per member, made by the ship step. No record lists the landing; the team owns merge order and the deploy tolerance for one side landing first. All three tools reach a second root, each through its own grant, and `cross-tool-strategy.md` § Reaching a Second Root records the three locations. OpenCode's grant has no read and write split, so allowing a member allows edits to it. The member list is restated in four places: the layout, the two committed grants, the Copilot user config, and the claude-dev mounts. The doctor gates the committed ones and reports the rest.

## Implementation

Change 1 of 3 landed 2026-09-19; changes 2 and 3 are pending. The spike precedes them, over an umbrella with one sibling member. It checks rules-file loading from an added directory, a claude-dev launch with the member mounted read-write, whether OpenCode's `external_directory` rule resolves a project-relative path, and a non-interactive Copilot run under a persisted `allowed_directories` entry. A failed check falls back to option 3 for that tool and records it here. The three changes, in order, each battery-gated:

1. **Landed 2026-09-19.** The workspace fan-out in the git gateway, the emit module, the grading features, and `schemas/scratch/review-plan.schema.json`. The single-repository path is proven unchanged by the three contract nets against a worktree at the previous commit. The grading fuzzer builds workspace projects from then on, and its `--single-repository` switch reproduces the single-repository net. The `stack`, `contracts`, and `depends_on` fields are parsed and validated but read by nothing yet.
2. **Presence and pushback.** Member presence in the layout, the doctor, and `scripts/gate.sh`, with the doctor's grant-drift check. The gate's member loop, which the bookstore's `stack.sh` hand-writes until then. Design triage refusing a contract change while a dependent is absent, the review-plan-time safety net, and the grader naming absent members. The doctor holding `contracts` and `depends_on` to the product design's module map.
3. **The module role.** Its roster in `doctor-expectations.toml`, role detection in the stack registry, `init` and `materialize` scaffolding, and `init` writing the Claude Code, sandbox, and OpenCode grants from the table. Per-member probe and conventions composed from the declared stack. The product-role managed chapter, and a workspace section in `docs/adoption-guide.md`.

The design is stated in [`../product-workspace.md`](../product-workspace.md), whose § Implementation Status names which mechanism runs today.
